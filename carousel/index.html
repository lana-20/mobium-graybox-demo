Why it flakes03 / 10

Only the app knows it is still busy.

MobiumApp's Busy Demo starts 0.4 to 1.6 seconds of work and leaves the old rows up while it runs. A tap that comes before the new rows lands on a row that is about to go.

The fix, in the app04 / 10

So the app says when it is busy.

const refresh = () => {
  GrayBox.busy('quiet');
  // the work, then the new rows
};
// once the new rows have rendered:
GrayBox.idle('quiet');

MobiumApp links Mobium's gray-box library, in Swift and Kotlin. It writes one line to the device log for each change, and Mobium already reads that log:

MOBIUM-GRAYBOX busy=1 tag=quiet
MOBIUM-GRAYBOX still busy=1
MOBIUM-GRAYBOX busy=0 tag=quiet

The edges07 / 10

A wait that knows when to stop.

Work that never endsRefused after 10 seconds, naming what kept the app busy.
The app goes home, or crashesNot waited on. Busy is a lease the app renews twice a second, and a dead app stops renewing it.
The log stream dropsThe result says Mobium could not hear the app, and it listens again.
Every result says what it waited for“waited 955 ms (busy: quiet)”, “the app was idle”, or why it did not wait.

All six edge checks pass on all four devices.

The trust model09 / 10

A door the app opens, and only for the test.

The app opts inIt links a small library and says what it is doing. Work it does not declare is not waited for.
Silent unless the test turns it onA launch argument on iOS, an intent extra on Android. Anyone opening the same build sees nothing.
Only what the app registeredA hook is called by name. Any other name is refused, with the list of names that exist.
Builds made for testingKeep hooks out of what ships. An app without the library is driven the ordinary way.
